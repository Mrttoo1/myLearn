# 第一课：从点击保存到数据库提交

本课只需要弄清楚一件事：点击页面上的“保存记录”后，数据经过了哪些地方？

## 先亲手操作一次

1. 按根目录 README 启动数据库、后端和前端。
2. 从页头进入“学习记录”（`http://127.0.0.1:5173/notes`），填入标题“第一次理解前后端配合”，正文自行填写。首页是课程演示，不是记录表单。
3. 按 F12，在浏览器开发者工具的 Network 中筛选 Fetch/XHR。
4. 点击保存，找到 `POST /api/notes` 请求。
5. 观察请求正文、响应状态 `201` 和响应数据里的 `id`。
6. 刷新页面，观察 `GET /api/notes` 返回刚才保存的记录。

数据能在刷新后保留，是因为它存进了 PostgreSQL；Vue 内存中的状态在刷新时会重新创建。

## 第一步：前端把对象转换成 JSON

看 `frontend/src/api/notes.ts` 的 `createNote`。

`JSON.stringify(data)` 将 JavaScript 对象转换为 JSON 文本，使用 POST 发送到 `/api/notes`。Vite 开发代理再把这个请求转给后端。

请求正文例如：

```json
{
  "title": "第一次理解前后端配合",
  "content": "前端发请求，后端处理业务，数据库保存数据。"
}
```

这里的路径是接口地址，不对应服务器上的某个静态文件。

## 第二步：后端找到路由函数

先看 `backend/app/main.py` 的 `include_router`，再看 `backend/app/routers/notes.py` 的 `create_note`。

- `prefix="/api"` 与路由模块的 `prefix="/notes"` 拼出 `/api/notes`。
- `@router.post` 规定只有对应地址的 POST 请求进入这个函数。
- `data: NoteInput` 表示请求正文要按照 NoteInput 的规则解释和校验。
- `Depends(get_session)` 表示数据库会话由后端准备，前端不用传数据库连接。

如果标题为空，FastAPI 在调用业务函数前返回 `422`；不符合要求的数据不会进入正常保存流程。

## 第三步：区分接口结构和数据库模型

对照 `schemas.py` 与 `models.py`：

| 结构 | 对应问题 | 例子 |
| --- | --- | --- |
| `NoteInput` | 客户端可以提交什么？ | 标题、正文 |
| `NoteRead` | 客户端会收到什么？ | 标题、正文、id、时间 |
| `Note` | 数据库表如何组织？ | 列类型、主键、默认时间、约束 |

客户端不能决定新记录的 id 和创建时间。这些字段由数据库产生，再通过响应结构返回。

后端仍然要校验参数：浏览器里的 `required` 和 `maxlength` 只改善页面体验，其他客户端可以绕过页面直接请求接口。

## 第四步：业务函数提交事务

看 `backend/app/services/notes.py` 的 `create_note`：

```python
note = Note(title=data.title, content=data.content)
session.add(note)
session.commit()
session.refresh(note)
return note
```

逐句理解：

1. 创建一个代表新记录的 Python 对象。
2. 把它登记到本次会话里，准备写入。
3. 提交事务，让修改正式保存到数据库。
4. 从数据库重新读取对象，得到数据库生成的字段。
5. 把结果返回给路由层。

**Session 不是登录会话。**这里的数据库 Session 是一次数据库操作的工作空间。多个操作可以放在同一事务里，全部成功才提交，出错则回滚。

本例每次写入只有一条记录。以后有“创建订单并扣减库存”等多步操作时，再学习如何把多步操作放进同一个事务。

## 第五步：返回 JSON 并更新页面

路由的 `response_model=NoteRead` 指定响应结构。Pydantic 根据对象属性生成数据，FastAPI 返回 JSON。

前端拿到成功响应后清空表单，并重新请求列表。页面显示的是后端查询到的数据。

删除接口返回 `204`，没有 JSON 正文，所以前端 `http.ts` 必须先处理这种情况。

## 看一眼真实的 SQL

把 `backend/.env` 中的 `SQL_ECHO` 改为 `true`，然后重启后端。配置在应用启动时读取，仅修改 `.env` 不会自动更新已创建的 Engine。

再新增一条记录，观察后端终端中的 `INSERT`、`COMMIT` 和后续 `SELECT`。也可以进入后端目录，启动 Python 交互环境：

```powershell
cd backend
.\.venv\Scripts\python.exe
```

然后在 Python 中逐行输入，最后多按一次回车结束缩进块：

```python
from sqlalchemy import text
from app.database import engine

with engine.connect() as connection:
    rows = connection.execute(text("SELECT id, title, created_at FROM notes ORDER BY id DESC"))
    for row in rows:
        print(row)
```

`text()` 表示这里要执行的是手写 SQL。输入 `exit()` 离开 Python。如果使用 Docker，也可以在项目根目录直接运行数据库客户端：

```powershell
docker compose exec db psql -U learn -d learn -c 'SELECT id, title, created_at FROM notes ORDER BY id DESC;'
```

观察结束后可将 `SQL_ECHO` 改回 `false`，再重启后端，让日志更简洁。

## 再认识一下数据库迁移

模型文件只是 Python 中的表结构描述，不会自动修改已经存在的数据库。

`migrations/versions/0001_create_notes.py` 是第一次建表的变更记录；`alembic upgrade head` 按版本执行尚未应用的迁移。重复执行不会重复建表。

以后需要给记录增加“标签”时，要同时考虑模型、接口结构、迁移和前端。本课先不做这一步。

## 用接口文档做三个小实验

打开 `http://127.0.0.1:8000/docs`，点击接口下的 **Try it out**：

1. 提交正常标题，观察返回 `201`，并在页面点击刷新确认数据出现。
2. 提交只有空格的标题，观察 `422`，确认没有新增记录。
3. 查询或删除不存在的 id，观察 `404` 和错误正文。

在学习记录里用自己的话回答：

- 为什么前端校验之后，后端还要校验？
- `add`、`commit`、`refresh` 分别做了什么？
- 修改 Python 模型后，为什么还需要数据库迁移？
- `201`、`204`、`404`、`422` 分别告诉客户端什么？
